## 正文

```text
前一阵用 Codex 的 Fast Mode 用习惯了，回到 DSH（DeepSeek Harness）就觉得首字慢。
第一反应是去调提示词让模型少说点 —— 但这不就是偷工减料么，我要的是同一个模型、同样的思考量，单纯把服务端排队优先级提上去。

OpenAI 那边有文档化的参数：请求体里带 service_tier: "priority"。问题是 DSH 的请求体是深冻结的，
插件层改不了，只能在 HTTP 序列化之后注入。于是写了个 fetch 钩子，在 body 里塞这一个字段，别的一概不动。

麻烦的地方在于「到底有没有用」。
我做了个 A/B：同一个模型、同一个推理强度、同一句极小 prompt（就让它回一个 ok），
交错跑 standard / fast 各 3 轮，比首字延迟。8 次探测的结果是：

  +5.9%  +18.5%  +1.3%  +5.2%  +23.6%  -7.8%  -0.1%  +9.7%

看着有两个两位数，挺爽对吧？但我重跑就没了。那个 +23.6% 是单轮跑出来的，
后来连跑三次是 -7.8%、-0.1%、+9.7%。同一台机器、同一个端点、同一分钟。

结论：我这个中转对 DeepSeek-V4.1-Flash 和 V4-Pro 都不给优先队列，参数是被接受了（没报 400/422），
但服务端没当回事。中位数 +5.5%，在噪声里。

所以插件现在会这么干活：
- 参数只在两种情况下注入：厂商文档明确写了（OpenAI），或者你亲手跑够 3 轮探测、最近 3 次里至少 2 次真的快 ≥15%
- 单轮探测一律不下结论（我自己被那个 +23.6% 骗过一次）
- 判定为「无效」时，开关照样能拨，但旁边会写明「Fast 未生效」——不假装

顺带做了点别的：TTFT / tok/s 从真实流里量（不是估），429 读 Retry-After 后压住下一个请求而不是硬怼。

写这篇不是想说这东西多牛，相反：**它是第一个老实告诉你「你这个端点没有快车道」的工具**。
如果你正好在用 OpenAI 官方 API（那边文档写了优先档），或者你知道哪家中转真开了 priority，
跑一下探测把结果告诉我，我想攒一批真实数据 —— 现在这个仓库里只有我一个人的样本。

仓库：https://github.com/iambubu0523/dsh-turbo
安装（不用 npm 账号）：插件面板填 github:iambubu0523/dsh-turbo

MIT，零依赖，卸载干净（删两个 JSON 就没了）。
```
